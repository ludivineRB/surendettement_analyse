===============================================================================
1. OBJECTIF DU LOT
===============================================================================

Ce deuxième lot prépare le projet à quitter progressivement une exécution
principalement locale fondée sur SQLite pour aller vers une exploitation
industrialisée avec PostgreSQL, Docker et plusieurs environnements.

Il poursuit six objectifs :

1. versionner les évolutions du schéma de la base opérationnelle ;
2. transférer les données SQLite existantes vers PostgreSQL sans les écraser ;
3. formaliser les sauvegardes et restaurations PostgreSQL ;
4. distinguer les environnements développement, recette et production ;
5. vérifier automatiquement la disponibilité des services ;
6. fournir une commande de contrôle réutilisable dans une future CI.

Ce lot ne met pas encore l’application en production. Il fournit le socle
technique permettant de le faire de manière contrôlée et reproductible.

Aucune donnée existante n’a été supprimée ou remplacée. Aucun commit ou push
Git n’a été effectué.

3. MIGRATIONS DE SCHÉMA VERSIONNÉES
===============================================================================

Fichier :

src/storage/schema_migrations.py

Rôle :

Ce module fournit un registre minimal de migrations compatible avec SQLite et
PostgreSQL. Il évite de dépendre uniquement de create_all(), qui crée les
objets absents mais ne permet pas, à lui seul, de savoir quelles évolutions de
schéma ont déjà été exécutées.

3.1. Table de suivi

Le système crée une table :

schema_migrations

Elle contient :

- version : identifiant unique de la migration ;
- description : description lisible de l’évolution ;
- applied_at : date UTC d’application.

Cette table constitue la mémoire technique du schéma. Chaque migration ne doit
être exécutée qu’une seule fois par base.

3.2. Migrations initiales

Deux versions ont été définies.

001_application_schema

- crée le schéma SQLAlchemy de l’application ;
- utilise Base.metadata.create_all() ;
- crée uniquement les tables absentes ;
- ne supprime aucune table ni aucune donnée.

002_operational_indexes

- crée l’index ix_pipeline_runs_name_started sur :
  pipeline_runs(pipeline_name, started_at) ;
- crée l’index ix_source_documents_period_status sur :
  source_documents(reference_period, extraction_status) ;
- crée l’index ix_observations_period_level_code sur :
  observations(reference_period, geographic_level, geographic_code).

Ces index accélèrent les consultations les plus courantes :

- historique d’exécution d’un pipeline ;
- contrôle des documents par période et statut d’extraction ;
- recherche des observations par période et territoire.

Les instructions CREATE INDEX utilisent IF NOT EXISTS. Elles restent donc
réexécutables sans créer de doublon.

3.3. Idempotence

La fonction apply_migrations() :

1. crée la table schema_migrations si elle n’existe pas ;
2. récupère les versions déjà enregistrées ;
3. ignore les migrations déjà appliquées ;
4. exécute les nouvelles migrations dans l’ordre déclaré ;
5. enregistre chaque version après son exécution.

Elle renvoie un rapport séparant :

- applied : migrations nouvellement appliquées ;
- already_applied : migrations déjà présentes.

L’ensemble est exécuté dans une transaction gérée par SQLAlchemy.

3.4. Limites actuelles

Ce registre est volontairement léger. Il convient au schéma actuel, mais ne
remplace pas encore un outil complet tel qu’Alembic pour :

- les modifications complexes de colonnes ;
- les migrations de données élaborées ;
- les branches de migrations ;
- la génération automatique de révisions ;
- les rétrogradations de schéma.

Une adoption future d’Alembic reste possible. Les versions présentes devront
alors être reprises dans la base de référence afin d’éviter leur réexécution.

4. TRANSFERT SQLITE VERS POSTGRESQL
===============================================================================

Fichier :

src/storage/migrate_to_postgres.py

Rôle :

Ce module copie les données de la base opérationnelle SQLite actuelle vers une
base PostgreSQL déjà accessible.

4.1. Conditions préalables

- le fichier SQLite source doit exister ;
- la cible doit réellement utiliser le dialecte PostgreSQL ;
- la cible doit être accessible avec l’URL fournie ;
- le pilote PostgreSQL psycopg doit être installé ;
- l’utilisateur PostgreSQL doit pouvoir créer les tables et insérer les
  données.

Le programme refuse explicitement une cible qui n’est pas PostgreSQL.

4.2. Déroulement

Le transfert :

1. ouvre la base SQLite source ;
2. ouvre la base PostgreSQL cible ;
3. applique les migrations de schéma sur PostgreSQL ;
4. inspecte les tables présentes dans SQLite ;
5. reprend l’ordre des tables défini par les métadonnées SQLAlchemy ;
6. lit les lignes source ;
7. les insère dans les tables PostgreSQL correspondantes ;
8. ignore les conflits de clés primaires ;
9. recale les séquences des clés entières auto-incrémentées ;
10. produit un rapport par table.

4.3. Protection contre l’écrasement

Les insertions PostgreSQL utilisent ON CONFLICT DO NOTHING lorsqu’une clé
primaire est disponible.

Conséquences :

- une ligne déjà présente n’est pas remplacée ;
- une nouvelle ligne est insérée ;
- une relance ne duplique pas les lignes ayant la même clé primaire ;
- le transfert est adapté à une reprise après interruption.

Il s’agit d’une stratégie de conservation. Ce mécanisme ne met pas à jour une
ligne PostgreSQL déjà existante si son contenu diffère de SQLite.

4.4. Rapport

Le rapport indique :

- le chemin de la source ;
- le dialecte de la cible ;
- le nombre de lignes insérées par table ;
- le nombre de lignes ignorées par table.

4.5. Mode simulation

L’option --dry-run inspecte les lignes disponibles sans les insérer. Dans ce
mode, toutes les lignes détectées sont comptabilisées comme ignorées.

4.6. Commande

Exemple :

.venv/bin/python -m src.storage.migrate_to_postgres \
  --source data/processed/surendettement.db \
  --target-url "postgresql+psycopg://UTILISATEUR:MOT_DE_PASSE@HOTE:5432/BASE"

La cible peut également être fournie avec :

TARGET_DATABASE_URL

Exemple de simulation :

TARGET_DATABASE_URL="postgresql+psycopg://..." \
.venv/bin/python -m src.storage.migrate_to_postgres \
  --source data/processed/surendettement.db \
  --dry-run

4.7. Séquences PostgreSQL

Après insertion, le programme recherche une unique clé primaire entière
auto-incrémentée. Il utilise ensuite pg_get_serial_sequence et setval pour
aligner la séquence sur la plus grande clé copiée.

Le contrôle du type entier est important : les tables possédant une clé
primaire textuelle ne doivent pas être traitées comme si elles utilisaient une
séquence PostgreSQL.

4.8. Limites actuelles

- le transfert n’a pas été exécuté sur une base PostgreSQL réelle pendant ce
  lot, afin de ne pas créer ni modifier une infrastructure externe sans cible
  explicitement fournie ;
- ON CONFLICT DO NOTHING ne synchronise pas les mises à jour ;
- l’outil copie les tables appartenant au modèle SQLAlchemy connu ;
- les très grandes tables sont actuellement chargées en mémoire table par
  table et ne sont pas encore copiées par lots ;
- une validation fonctionnelle après transfert reste nécessaire :
  comptage, sommes de contrôle, périodes, indicateurs et scores.

6. SAUVEGARDE POSTGRESQL
===============================================================================

Fichier :

docker/backup_postgres.sh

Rôle :

Créer une sauvegarde logique de PostgreSQL à partir du service postgres de
Docker Compose.

6.1. Fonctionnement

Le script :

- active l’arrêt immédiat en cas d’erreur ;
- lit BACKUP_DIR ou utilise ./backups ;
- lit POSTGRES_DB ou utilise surendettement ;
- lit POSTGRES_USER ou utilise surendettement ;
- crée le dossier de sauvegarde ;
- applique umask 077 pour protéger le fichier créé ;
- exécute pg_dump dans le conteneur PostgreSQL ;
- utilise le format custom de PostgreSQL ;
- exclut les propriétaires et privilèges spécifiques ;
- vérifie que le fichier final existe et n’est pas vide ;
- affiche le chemin de la sauvegarde.

Format du nom :

BASE_YYYYMMDDTHHMMSSZ.dump

La date est exprimée en UTC.

6.2. Commande

POSTGRES_PASSWORD="..." sh docker/backup_postgres.sh

Avec un dossier choisi :

BACKUP_DIR="/chemin/securise" \
POSTGRES_PASSWORD="..." \
sh docker/backup_postgres.sh

6.3. Propriétés

Le format custom permet une restauration avec pg_restore et offre davantage de
contrôle qu’un simple fichier SQL texte.

Le mot de passe n’est pas écrit dans le script. Docker Compose le reçoit par
variable d’environnement.

6.4. Limites

- le service postgres doit être démarré ;
- Docker Compose doit être disponible ;
- la rétention et la rotation des sauvegardes ne sont pas encore automatisées ;
- la copie vers un stockage externe n’est pas incluse ;
- le chiffrement externe du fichier n’est pas inclus ;
- une sauvegarde n’est considérée fiable qu’après un test de restauration.

7. RESTAURATION POSTGRESQL
===============================================================================

Fichier :

docker/restore_postgres.sh

Rôle :

Restaurer une sauvegarde custom dans PostgreSQL en imposant une confirmation
explicite.

7.1. Protections

Le script exige :

- exactement un chemin de sauvegarde ;
- un fichier existant ;
- un fichier non vide ;
- la variable CONFIRM_RESTORE=yes.

Sans cette confirmation, l’opération est refusée.

7.2. Commande

CONFIRM_RESTORE=yes \
POSTGRES_PASSWORD="..." \
sh docker/restore_postgres.sh backups/BASE_DATE.dump

7.3. Comportement

pg_restore utilise :

- --clean : suppression des objets restaurés déjà présents ;
- --if-exists : évite les erreurs lorsque certains objets sont absents ;
- --no-owner : ne restaure pas les propriétaires d’origine ;
- --no-privileges : ne restaure pas les privilèges d’origine ;
- --exit-on-error : interrompt la restauration dès la première erreur.

7.4. Avertissement important

La restauration est destructive pour les objets concernés, car --clean
remplace le contenu de la base cible par celui de la sauvegarde.

Avant toute utilisation réelle, il faut :

1. vérifier précisément l’environnement ciblé ;
2. faire une sauvegarde de l’état actuel ;
3. interrompre ou mettre en lecture seule les écritures applicatives ;
4. restaurer ;
5. appliquer les migrations éventuellement plus récentes ;
6. exécuter les contrôles de qualité ;
7. remettre les services en fonctionnement.

Le script a été contrôlé syntaxiquement, mais aucune restauration réelle n’a
été déclenchée pendant ce lot.

10. ENVIRONNEMENT DE PRODUCTION
===============================================================================

Fichier :

docker/compose.production.yaml

Ce fichier renforce docker/compose.yaml.

10.1. PostgreSQL

- restart: unless-stopped ;
- délai d’arrêt de 30 secondes.

Ce délai permet à PostgreSQL de terminer proprement ses opérations lors de
l’arrêt du conteneur.

10.2. API

- restart: unless-stopped ;
- init: true pour une meilleure gestion des signaux et processus ;
- healthcheck HTTP sur /api/data/health ;
- vérification toutes les 30 secondes ;
- délai maximal de 10 secondes ;
- trois échecs avant déclaration d’indisponibilité ;
- délai initial de 30 secondes.

Le contrôle HTTP utilise Python urllib déjà présent dans l’image. Il n’ajoute
donc pas de dépendance système à curl.

10.3. Streamlit

- restart: unless-stopped ;
- init: true ;
- healthcheck sur /_stcore/health ;
- mêmes intervalles et délais que l’API ;
- démarrage conditionné par une API déclarée saine.

10.4. Chaîne de dépendances

L’ordre logique est :

PostgreSQL sain
    -> API démarrée et saine
        -> Streamlit démarré et surveillé

Cela limite les erreurs de démarrage provoquées par une dépendance encore
indisponible.

10.5. Commande indicative

POSTGRES_PASSWORD="secret-fort" \
docker compose \
  -f docker/compose.yaml \
  -f docker/compose.production.yaml \
  up --build -d

10.6. Secrets

Le mot de passe PostgreSQL reste obligatoire dans docker/compose.yaml :

POSTGRES_PASSWORD

Aucun mot de passe réel n’a été ajouté au dépôt.

Pour une production définitive, il reste recommandé d’utiliser un gestionnaire
de secrets ou les secrets du moteur d’orchestration au lieu d’une variable
saisie dans le terminal.

14. PROCÉDURE CONSEILLÉE POUR LA PREMIÈRE MIGRATION RÉELLE
===============================================================================

1. Créer une instance PostgreSQL de recette.
2. Définir un mot de passe robuste hors du dépôt.
3. Démarrer PostgreSQL.
4. Sauvegarder la base SQLite et les fichiers analytiques.
5. Exécuter le transfert en recette.
6. Comparer les nombres de lignes table par table.
7. Contrôler les périodes, territoires, indicateurs et unités.
8. Recalculer ou vérifier les scores régionaux et départementaux.
9. Démarrer l’API avec DATABASE_URL pointant vers PostgreSQL.
10. Vérifier /api/data/health et les routes analytiques.
11. Démarrer Streamlit et vérifier les filtres, cartes et exports.
12. Tester une sauvegarde PostgreSQL.
13. Restaurer cette sauvegarde dans une deuxième base de test.
14. Rejouer les contrôles fonctionnels.
15. Documenter le résultat et seulement ensuite préparer la production.

- documents en échec ou à vérifier.

===============================================================================
16. POINTS D’ATTENTION
===============================================================================

1. Une migration de schéma réussie ne garantit pas la qualité des données.
2. Un transfert sans conflit ne garantit pas que la cible est complète.
3. ON CONFLICT DO NOTHING protège les lignes présentes mais peut masquer une
   différence de contenu ; un audit comparatif reste nécessaire.
4. Les sauvegardes doivent être copiées hors de l’hôte PostgreSQL.
5. Une restauration doit être testée périodiquement.
6. Les environnements doivent employer des bases, volumes et secrets distincts.
7. La production doit utiliser HTTPS via un proxy ou une plateforme adaptée.
8. L’accès PostgreSQL ne doit pas être exposé publiquement.
9. L’API publique devra recevoir authentification, quotas et journalisation.
10. Les journaux ne doivent pas contenir de secrets ni de données sensibles.
11. Les images Docker devront être versionnées précisément.
12. La CI devra vérifier PostgreSQL réellement, et pas seulement SQLite.
